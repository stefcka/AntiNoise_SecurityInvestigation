# Cloud Threat Detection & Investigation Platform

An open-source investigation layer for SOC analysts: it turns cloud identity and VM telemetry into
evidence-backed incidents, scores them with transparent deterministic logic, uses a self-hosted model
only to explain them, and runs containment only after an analyst approves it. Everything lands in a
hash-chained audit ledger.

```
Azure telemetry ──► your server ──► deterministic detection ──► local LLM ──► analyst
```

The model runs on your own hardware (Ollama or any OpenAI-compatible server), so incident data never
goes to a third-party AI service. The only outbound calls are to Microsoft, for collection and for
approved response actions.

Azure / Entra ID / Microsoft 365 only for the hackathon. The event model is provider-neutral so AWS
and Google adapters can be added later without touching detection, scoring, or the UI.

## Run it in two minutes

```bash
python -m venv .venv && source .venv/bin/activate      # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env                                   # works with every value left blank
uvicorn app.main:app --reload
```

For the AI investigator, run a local model (details in `docs/local_llm.md`):

```bash
ollama pull qwen2.5:7b          # defaults in .env.example point at Ollama on localhost:11434
```

Open http://127.0.0.1:8000 and click **Replay sample telemetry**. You get six incidents from five
datasets immediately; AI assessments fill in one by one in the background. With no model running,
the AI panel shows a clearly-labelled deterministic summary and everything else works. With no
Microsoft credentials, every action is simulated and labelled as such.

```bash
pytest -q                        # 14 tests: detection, scoring, validator, local LLM, response, audit
python scripts/eval_local_model.py   # compare local models on the sample incidents
python scripts/run_pipeline.py   # same pipeline from the command line
python scripts/verify_ledger.py  # check the audit hash chain
python scripts/reset_demo.py     # archive data/ and start clean (nothing is deleted)
```

## How it works

```
fixtures/*.json  or  live Graph / O365 collectors
        │  (records in the provider's own format)
        ▼
adapters/        normalize  → NormalizedEvent        (one function per source)
detection/rules  15 rules   → DetectionSignal        (one event in, zero or more signals out)
detection/correlation  4 chains → Incident           (same user/app/VM, time window, required steps)
detection/scoring  severity + confidence, every point has a named reason
ai/llm           local model client (Ollama /api/chat or OpenAI-compatible), background worker
ai/investigator  explanation + Q&A  → ai/validator strips anything not grounded in the incident
response/executor  analyst approves → LIVE (only if enabled) or SIMULATED → verify → record
ledger.py        append-only JSONL, each record hashes the previous one
```

The AI never creates incidents, never sets scores, and never chooses action targets. It can only pick
action names from the incident's `allowed_actions`; the validator removes anything else, and removes
findings that cite event IDs not in the incident. App names, inbox rule names and command lines are
treated as untrusted data in the prompt. Scenario A's app name contains a live prompt-injection
attempt to show this.

## Scenarios in the sample data

| Dataset | Incident | Severity / confidence | Shows |
|---|---|---|---|
| `a_oauth_malicious_consent` | Malicious OAuth consent: consent, sensitive scopes, token use from attacker IP, mail and file access | Critical 95 / High 90 | Flagship attack, prompt-injection attempt, live grant revocation |
| `e_oauth_migration_benign` | Same technical pattern from an internal migration tool | Critical 100 / Medium 65 | False-positive workflow: severity and confidence diverge |
| `b_session_misuse` | Sign-in outside allowed countries, new MFA method, forwarding inbox rule | High 70 / Medium 60 | Account takeover without baselining |
| `c_privilege_escalation` | Self-assigned Global Admin, then app credential and owner added | Critical 100 / Medium 52 | Missing sign-in logs lowers confidence, stated as a limitation |
| `d_vm_suspicious_activity` | Windows: Word spawns encoded PowerShell, drops IOC binary. Linux: nginx spawns `curl \| sh`, runs from /tmp | Critical 90 / High 80 and High 65 / Medium 50 | Endpoint-only incidents, VM isolation |

Sample telemetry uses the real provider record shapes (Graph `directoryAudits` and `signIns`, Office 365
Management Activity API, Sysmon), so the same normalizers run on live data. The fixtures are generated by
`scripts/build_fixtures.py`; edit that file to change the story.

## What is real, what is simulated

| Capability | Status |
|---|---|
| Normalization, 15 detection rules, 4 correlation chains, severity, confidence | Real, tested |
| Live collection: Entra audit logs | Real (works on Entra ID Free) |
| Live collection: sign-in logs | Real, needs Entra ID P1/P2; a 403 is reported as unavailable telemetry |
| Live collection: Exchange / OneDrive audit | Real, needs M365 licences + auditing; hours of latency, so capture ahead of the demo |
| `REVOKE_OAUTH_GRANT`, `DISABLE_APPLICATION`, `REVOKE_USER_SESSIONS` | Live when listed in `LIVE_ACTIONS` with responder credentials; otherwise simulated |
| `ISOLATE_VM` + Restore network | Live when enabled and the isolation NSG exists; otherwise simulated |
| `DISABLE_USER`, `ESCALATE_INCIDENT`, `NO_ACTION` | Always simulated (recorded only) |
| AI investigator and chat | Local model via Ollama or OpenAI-compatible server; labelled deterministic fallback when unreachable. Request formats are tested against mocks, not yet against a real model server |
| Cross-domain identity + VM correlation | Not built (P2 stretch) |

The live Graph, O365 and Azure SDK code paths have not been run against a tenant yet. Test them on
day one: see `docs/azure_setup.md`.

## Adding things

- **A rule:** write a `match(event, ctx)` function in `detection/rules.py` and add a `Rule(...)` to `RULES`.
- **A scenario:** add a `Chain(...)` to `CHAINS` in `detection/correlation.py` and its actions to `response/catalog.py`.
- **A provider (after the MVP):** add `adapters/aws.py` returning `NormalizedEvent` fields and register it in `adapters/__init__.py`.
